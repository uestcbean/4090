# 项目契约 v0.1：我们到底在优化什么？

创建日期：2026-10-28。学习验收日期：2026-10-29。状态：步骤 00 概念学习完成。
本文件由助手根据已有约定整理；作者通过对话计算与判断完成本轮引导式验收，具体回答与纠正见实验报告。所有数字目标都是初始假设，不是实测性能。

## 服务场景与目标

在 Windows + WSL2、单张 RTX 4090 24GB 上运行中文通用对话模型，为多位用户提供流式响应。
第一阶段候选模型为 Qwen3-8B，固定 non-thinking 模式；具体 revision 和引擎版本在部署阶段冻结。

核心目标：在输出质量达标、工作负载一致的条件下，提高满足响应延迟要求的请求处理能力。
同时记录总输出吞吐、错误/拒绝率、显存和功率，不能只追求 GPU busy=100%。

## 四个指标

设客户端发送时间为 t0，首个内容 token 到达时间为 t1，最后一个内容 token 到达时间为 tn，共输出 N 个 tokens。
空的 role/event 帧不算首个内容 token；流式网络 chunk 不一定只含一个 token。

| 指标 | 定义 | 用户或系统关心的问题 |
|---|---|---|
| TTFT | t1 - t0，单位秒 | 等多久才开始看到内容？包含排队、prefill、网络等时间 |
| 请求级 TPOT | (tn - t1)/(N - 1)，单位秒/token；N<2 不计算 | 开始响应后，平均生成节奏有多快？ |
| 输出吞吐 | 测量窗口内实际输出 token 数 / 窗口时长 | 整个服务每秒产出多少 tokens？ |
| goodput | 窗口内成功完成且满足逐请求延迟门槛的请求数 / 窗口时长 | 每秒完成多少体验达标的请求？ |

TPOT 是请求内平均值，可能掩盖中间的长停顿；后续同时查看可测的间隔/停顿和总时延。
所有窗口与请求边界规则会在步骤 05 固定，不能把发送窗口、排空时间和完成窗口混用。

## 初始工作负载与 SLO

SLO（Service Level Objective）是服务质量目标。本项目区分逐请求门槛与整组请求的统计目标。

- 短对话性能组：目标输入约 512 tokens、输出约 128 tokens，由 tokenizer 校验；具体生成/终止策略在步骤 05 固定。
- 短对话逐请求门槛：成功、TTFT <= 1 秒、TPOT <= 50 ms/token。质量评估必须先通过，才允许候选配置参与比较。
- 短对话统计目标：p95 TTFT <= 1 秒、p95 请求级 TPOT <= 50 ms/token；同时报告联合达标率、错误、拒绝与超时。
- p95 的含义：约 95% 的样本不超过该值。两个指标各自有 95% 达标，不代表同一批请求联合也有 95% 达标。
- 长输入组：初始计划输入约 4096 tokens、输出约 128 tokens；单独报告，不套用短对话 SLO。
- 混合组：在短/长组分别测清楚后固定混合比例，并保留分组结果。
- 质量门槛、长输入 SLO、总体成功率和联合达标率目标尚未冻结，分别在步骤 03/05 建立；未冻结前不声称可正式上线。

50 ms/token 对应约 20 tokens/s 的平均生成速率，是单请求生成节奏，不能当作全服务总吞吐。
SLO 可以因业务或环境认识变化而修订，但要记录理由和新版本，并对基准与候选按新口径一起重测，不能事后只放宽候选条件。

## 学习练习：以下全部是假设数据

同一质量水平、相同工作负载和请求到达序列。各配置在完整 10 秒窗口内收到并完成 100 个请求；每个输出 100 tokens。
没有跨窗口请求、错误或拒绝，以便专注理解统计。逐请求门槛沿用 TTFT <= 1 秒、TPOT <= 50 ms/token。

| 配置 | 窗口内总输出 tokens | 同时满足两项延迟门槛的成功请求数 |
|---|---|---|
| A | 10000 | 90 |
| B | 10000 | 60 |

练习 1：分别计算 A/B 的输出吞吐和 goodput。如果只看吞吐，会漏掉什么？

补充情景 C：同一个 10 秒窗口、相同 100 个请求到达序列；A 完成 80 个请求共输出 8000 tokens，余下 20 个尚未产出 token，完成者中 75 个达标；B 完成全部 100 个共输出 10000 tokens，其中 60 个达标。
练习 2：比较 C 中 A/B 的吞吐和 goodput，解释为什么“总吞吐提高”仍可能不是项目需要的优化。窗口外结果不计入此例的窗口指标，尚未完成的请求必须另外报告。
